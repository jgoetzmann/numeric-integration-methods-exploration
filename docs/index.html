A search for Runge-Kutta methods that work in 16-bit fixed point

Small chips often have no floating-point unit. This project built a system that searches for integrator coefficients that give the lowest error on such a chip. A container ran the search, with some stops, from 2026-08-29 to 2026-11-10. Code did every score, and the search could not change that code.

The run stopped for good on 2026-11-10, after cycle 17,364. No more compute goes to it. The code and the data stay here, and anyone can use them (MIT license).

The problem

An Arm Cortex-M0+ chip has no floating-point unit. Code on chips like this often uses Q15 numbers. A Q15 number is a 16-bit integer that holds a fraction from −1 to 1.

Each Q15 multiply rounds its result down (floor rounding). These small errors add up over many steps. On this chip, a multiply by ½ or ¼ is a cheap shift, but a multiply by ⅓ costs more cycles.

Textbook Runge-Kutta methods use coefficients that are best in exact arithmetic. They do not know about shift costs or floor rounding.

The question

Each method gets the same budget of 65,536 cycles. A cheap step gives more steps. Which coefficients give the lowest error in Q15?

How it works

Each search cycle has six steps. Select a step to see what it does.

Direct

A language model writes a JSON directive for the cycle. The directive can only make the search narrower. If it has an unknown key, the runner uses a fixed fallback. The model is optional. Without it, a fixed rule gives the direction.

Search

Early phases try every dyadic coefficient on a grid. A dyadic coefficient, like ½ or ⅜, has a power-of-two denominator, so a shift does the division. Later phases use CMA-ES over the stage matrix, with an exact projection onto the order conditions.

Verify

The pinned verifier checks the order conditions of each candidate in exact rational arithmetic. A candidate that fails does not get a score.

Score

The evaluator runs each candidate in Q15 on the search problems, at the same budget of 65,536 cycles. It finds the held-out error on four other problems. No optimizer reads those four problems.

Archive

Each result goes into an append-only archive with the hash of the code that scored it. A MAP-Elites grid keeps the best method in each cell of order, stage count and cost band.

Publish

At the end of the cycle, the container rebuilt the findings site and made commits. A watchdog on the host pushed them. No GitHub credential went into the container.

Why you can trust the scores

  • The container mounts the harness read-only, so the search cannot change its scorer.
  • A sha256 hash covers the 14 files that decide a score. The runner checks it at each start, and each record keeps it.
  • 91 golden and canary cases must pass before a cycle can start. The harness has 1,908 tests (2026-09-23).
  • The step compiled with GCC for the Cortex-M0+ agrees with Python in 144 of 144 cases. The demo above agrees in 154 of 154.

The 2025 project: an earlier attempt with machine learning

In 2025, an earlier project tried to make new Runge-Kutta tables with a neural generator, a surrogate model and an evolutionary search. It scored them in float64 on 10,000 generated ODEs. In September 2026, an audit checked its code and its claims.

What worked

The evaluation harness works from start to end for explicit tables: a Butcher-table stepper, an ODE generator and a SciPy reference solver. N9

What did not

The search started from RK4 and Dormand-Prince, and a score capped at 1 kept them. For this reason, it did not find them again. Nobody trained the generator. N2 N4

What the rk run does differently

It has an exact order check, a scorer that the search cannot change, tests on new problems and stated limits for each claim. R11 R4

R1The Q15 lead ★True, with limitsThe rk run

In Q15 with floor rounding, at a budget of 65,536 cycles, the champion 11e898cb has 2.95 times lower held-out error than midpoint. Midpoint is the best of the eight classical methods. This result uses the analytic m0plus_fast cost model and magnitude weighting.

Limits

This is an epoch-1 result. A later trace showed that the epoch-1 cost model put rk4 and rk38 in the wrong order. Epoch 2 uses a corrected model, but it did not measure this result again.

The search picked each elite by its held-out error, from 141,364 archived tableaus. This gives the lead a selection bias (the winner's curse).

The 2.95x is an RMS over four problems. The champion has lower error than midpoint on three of them and higher error on pendulum. Much of the gap comes from rc_thermal, where all classical methods stop near a quantization floor.

The lead changes with the cost basis and the weighting. With analytic cost and reference-norm weighting, it is 3.36x. With traced whole-step cost, it is 1.01x (magnitude) and 1.84x (reference-norm). If you remove one held-out problem, these two fall as low as 0.614x and 0.604x.

With median-anchor weighting, the lead is 1.1x on the analytic basis (lowest 0.814x) and 0.0494x on the traced basis. The source says that the weighting causes this last value because it magnifies pendulum. It does not mean that the champion loses by that factor.

The lead is a floor-rounding result. With round-to-nearest, at the same budget and cost model, rk38 gets 0.0263 held-out error. This is less than the 0.0286 of the champion with floor rounding. The comparison adds no cycles for the rounding, and only four classical methods ran in both rounding modes.

R5In float64, rk4 is much more accurate ★True, with limitsThe rk run

In float64, rk4 is much more accurate than the champion. Each method used the step count that the 65,536-cycle budget gives it. On the 7 validation problems where both completed, the float64 error of the champion was 1,992 to 420,975 times the error of rk4.

Limits

The champion is order 2 and rk4 is order 4. In the same runs, the classical order-2 methods are behind float64 rk4 by a similar margin.

Two wider comparisons used the seven search and held-out problems. They measure the arithmetic, not the coefficients. In 56 of 56 fixed-step comparisons at the same step counts, float64 rk4 had lower error than every Q15 run.

At tolerances of one Q15 least significant bit, the most accurate library solver was Radau on each problem. Its median error was 519 times lower than the error of the most accurate Q15 run.

Dormand-Prince (SciPy RK45) was one of the library solvers, but it was never the most accurate one. It never ran against the champion in the same arithmetic. The search was for Q15 floor arithmetic only, by design.

What the verdicts mean
  • True The cited files show it, as stated.
  • True, with limits The cited files show it, but only with the conditions in its limits. Quote it with those limits.
  • Not true The cited files do not show it, or they show something different.
  • A bug, not a result The number is real, but it measures a bug or a setup error, not the thing that its label names.

Run it yourself

The harness needs Python 3.12 or newer. The tests and one search cycle need no credentials and no API key.

  1. Clone this repository and go to the harness folder.
  2. Make a virtual environment and install the pinned packages from pyproject.toml.
  3. Check the verifier hash, then run the tests.
  4. Run one search cycle into two empty folders.
git clone https://github.com/jgoetzmann/numeric-integration-methods-exploration.git
cd numeric-integration-methods-exploration/harness
python -m venv .venv && . .venv/bin/activate
python -c "import tomllib; p=tomllib.load(open('pyproject.toml','rb'))['project']; print('\n'.join(p['dependencies']+p['optional-dependencies']['test']))" > req.txt
pip install -r req.txt
python -m rk_harness.verifier_hash --check
python -m pytest -q tests
RK_WORK_DIR=/tmp/rk-work RK_FINDINGS_DIR=/tmp/rk-findings python -m rk_harness.runner --once

To use the harness for a different search, read "Using it for another search" in the harness README. The container and the unattended run need Docker and a Windows host.
