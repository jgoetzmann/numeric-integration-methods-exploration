How they fit together

rk-harness is the code: the runner, the search, the pinned verifier, the site generator and a test suite that collected 1,908 tests on 2026-09-23. One command on the host brings up the container and a watchdog. The container mounts the harness read-only, so the search cannot change the code that scores it.

Each cycle the container appends scored records to rk-work, regenerates rk-findings (the findings site) and commits both. It never pushes: the watchdog does, so no GitHub credential enters the container. The one credential inside is the language model's sign-in file, mounted read-only. rk-work also keeps epoch 1 frozen under epochs/1/, with its validation, benchmark and trace documents. Epoch 1 froze after a trace found an error in its cost model.

rk-overview is rebuilt by hand from rk-work. Its tools recompute the analysis into tools/key_findings.json and generate the explainer pages. One of them is a browser demo that reimplements the Q15 solver in JavaScript and reproduces the Python evaluator in 154 of 154 fixture cases. The overview goes stale between refreshes, while the findings site rebuilds every cycle.

Novel-Numerical-Integration-Methods stands alone and shares no code or data with the rk run. What the two projects share is the question they asked.

The four rk repositories sit side by side in one private workspace, where the run is started and stopped. rk-dev, the private superproject that pins the four rk repos, is not linked. Every file cited as evidence for a claim is in one of the public repositories above, and the architecture diagrams show how the parts connect.

Rebuilding from the repositories

Clone numeric-integration-methods-exploration, then run from its root:

python tools/snapshot.py \
  --rk-workspace RK_WORKSPACE \
  --novel ML_2025_CLONE
python tools/build.py

RK_WORKSPACE is a directory holding clones of rk-harness, rk-work, rk-findings and rk-overview side by side, and ML_2025_CLONE is a clone of Novel-Numerical-Integration-Methods. tools/snapshot.py rewrites data/rk.json, data/novel.json and data/sources.json from those clones, recording the repository, commit, file and key behind each block of figures. tools/build.py reads only data/*.json and writes static pages to docs/ with the Python standard library. The same data gives byte-identical pages.

tools/snapshot.py leaves data/claims.json alone, since that file is written by hand. Check its claims against the new numbers before publishing a rebuild. Pass --out DIR to tools/build.py to write somewhere other than docs/, and run python -m pytest tests for the checks.
